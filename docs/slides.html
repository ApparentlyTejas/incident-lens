The idea

The database searches and calculates.
Claude explains.
Every number traces to a query that actually ran.

Incident Lens is an MCP server — 13 parameterized tools over BGL and OpenStack logs in SereneDB. Claude never writes SQL; the server does all searching and counting, and writes every call to a hash-chained evidence ledger before returning. Any Claude — yours, a judge's, anyone's — can connect and use it with their own account, from a terminal, Claude Desktop, or a web console built for this.

Architecture

Claude sees only what the server returns

Novelty · a tool the hackathon didn't ask for

What a frequency ranking hides, on purpose

concentration_anomalies ranks failures by how confined they are to one node or service — not how often they fire. The two rankings disagree, and the disagreement is the finding.

Buried by frequency

MACHINE CHECK DCR read timeout — 14,481 entries, confined to exactly 1 node out of the whole system. Ranked #33 by raw count: invisible past the default view.

Hidden in plain sight

idoproxydb hit ASSERT condition — 84,168 entries, 1 node. The single most concentrated failure in the whole corpus; a human scrolling a frequency list would never isolate it this cleanly.

A high ratio says "go check that one node's hardware first." A low ratio says "this is probably systemic." Both are exact counts — no ML, no guessing.

SereneDB at scale

4,955,757 rows. Every number below actually scanned them.

Load + index the full corpus: 3.4–9.2s tables, 5.9–9.6s inverted indexes, across repeated runs on a laptop — no pre-aggregation, no caching tricks.

The one outlier we found (search_logs, relevance mode) was root-caused and fixed, not hidden: a redundant time filter was silently disabling the index's fast top-k scoring path. Dropping the provably-redundant filter turned a ~1.5s query into ~150–215ms — same result, 9x faster.

The evidence ledger & answer contract

Four blocks. Every number carries a receipt — and the receipt book is tamper-evident.

1 · Observed

Measured facts only — scope, period, filters, [E-id]. Never len(rows) as a frequency.

2 · Hypotheses

Possible explanations, explicitly labelled. Never stated as fact.

3 · Recommended checks

Specific, ordered, each tied to an evidence id.

4 · Unknown

What the logs don't establish — cause, downtime, cost, customer impact. Never invented.

Tamper-evident, not just append-only

Every ledger entry's hash is sha256(previous entry's hash + this entry's own content). Hand-edit one stored number with a raw SQL UPDATE — bypassing every tool — and verify_ledger_integrity catches it and names the exact entry. Proven live in the web console's "Simulate Tamper" button, against a scratch copy that never touches the real ledger.

A browser you can watch it think in

The same 13 tools, with the evidence ledger made visible

Chat with Claude through the browser — same role prompts, same tools, called through the real Anthropic API. Every tool call lands on the right as it happens: the exact SQL, the exact count, the ledger hash, chained visibly to the one before it. Click any evidence id to replay it.

Not a second implementation — it's a thin UI over the exact same server. Tested over the real HTTP surface (overview, ledger status, tamper demo, evidence replay, path-traversal blocked), and the chat loop itself is driven end-to-end by a fake-client test harness, so the only genuinely untested piece is the literal network call to Anthropic — which needs a real key to exercise once, same as any MCP client.

Bonus · database row-level security

Per-team access, enforced by the database, not application code

SereneDB has no native ROW LEVEL SECURITY / CREATE POLICY — checked directly, not assumed. Built the same real guarantee from primitives it does support: one filtered view per team, straight from the ownership table, with that team's base-table grants revoked.
